## 1. 簡介

### 1.1 目的

定義 RD Design Copilot 的 RESTful API 契約，作為前後端協作 SSOT。

### 1.2 受眾

- 前端工程師（消費 API）
- 後端工程師（實作 API）
- QA（API 測試）
- 整合方（外部系統呼叫）

### 1.3 快速開始

```
Base URL（dev）: http://localhost:8000/api/v1
Base URL（prod）: https://copilot.delta.com/api/v1
Docs URL: {Base URL}/docs (Swagger UI auto-generated by FastAPI)
```

## 2. 設計原則與規範

### 2.1 RESTful 風格

| 規則 | 範例 |
|:-----|:-----|
| 資源命名用複數名詞 | `/projects`、`/contradictions` |
| 階層用 path params | `/projects/{project_id}/contradictions/{contradiction_id}` |
| 動作用 sub-resource 或 verb endpoint（少用） | `/triz/solve`、`/triz/verify` |
| HTTP 方法語義化 | GET（查）/ POST（建）/ PUT（全替換）/ PATCH（部分更新）/ DELETE |

### 2.2 命名約定

| 場景 | 規則 | 範例 |
|:-----|:-----|:-----|
| Path | kebab-case | `/projects/123/pre-cad-review` |
| Query / Body field | snake_case | `?page_size=20`、`{"project_id": "..."}` |
| Header | Kebab-Case | `X-Request-ID`、`Authorization` |
| Response field | snake_case | `{"created_at": "..."}` |

### 2.3 日期時間

- 使用 ISO 8601：`YYYY-MM-DDTHH:mm:ssZ`（UTC）
- 例：`2026-04-28T14:30:00Z`

### 2.4 統一回應格式

```json
{
  "success": true,
  "data": { /* 主要資料 */ },
  "message": "Optional human-readable message",
  "errors": null,
  "meta": {
    "request_id": "uuid",
    "timestamp": "2026-04-28T14:30:00Z"
  }
}
```

錯誤時：

```json
{
  "success": false,
  "data": null,
  "message": "Validation failed",
  "errors": [
    {
      "field": "email",
      "code": "INVALID_FORMAT",
      "message": "Email format is invalid"
    }
  ],
  "meta": { "request_id": "uuid", "timestamp": "..." }
}
```

## 3. 認證與授權

### 3.1 OAuth 2.0 + JWT

```
Authorization: Bearer <jwt_token>
```

- Token 在 HttpOnly Cookie（瀏覽器）或 header（API client）
- Refresh Token 機制：access 1h、refresh 7d

### 3.2 SSO/LDAP

對應 NFR-8：支援企業 SSO（SAML 2.0）與 LDAP 整合。

### 3.3 RBAC + Scopes

| Role | Scopes |
|:-----|:-------|
| `viewer` | `projects:read`, `kb:read` |
| `engineer` | `projects:write`, `triz:execute`, `kb:read` |
| `lead` | 上述 + `gates:approve`, `signoffs:create` |
| `admin` | 全部 |

### 3.4 Project-level Permission

每個 Project 有自己的 ACL（owner / collaborators / viewers）。

## 4. 通用 API 行為

### 4.1 分頁（Cursor-based）

```
GET /projects?cursor=eyJpZCI6MTIzfQ&limit=20

Response:
{
  "success": true,
  "data": [...],
  "meta": {
    "next_cursor": "eyJpZCI6MTQzfQ",
    "has_more": true
  }
}
```

### 4.2 排序

```
GET /projects?sort=-created_at,name
```
- `-` prefix = descending
- 多欄位用逗號分隔

### 4.3 篩選

```
GET /contradictions?type=TC&severity=Fatal&status=open
```

### 4.4 Partial Response

```
GET /projects/123?fields=id,name,status
```

### 4.5 展開關聯

```
GET /projects/123?expand=brief,owner
```

### 4.6 Idempotency

對 POST/PATCH/DELETE，client 可帶 `Idempotency-Key` header：

```
Idempotency-Key: <uuid>
```

伺服器在 24h 內回傳相同結果。

## 5. 錯誤處理

### 5.1 HTTP Status Codes

| Code | 用途 |
|:-----|:-----|
| 200 OK | 成功 |
| 201 Created | 建立成功 |
| 204 No Content | 刪除成功 |
| 400 Bad Request | 請求格式錯誤 |
| 401 Unauthorized | 未認證 |
| 403 Forbidden | 已認證但無權限 |
| 404 Not Found | 資源不存在 |
| 409 Conflict | 資源衝突（如重複建立） |
| 422 Unprocessable Entity | 驗證失敗 |
| 429 Too Many Requests | Rate limit |
| 500 Internal Server Error | 伺服器錯誤 |
| 503 Service Unavailable | 服務暫時不可用（如 LLM 失效） |

### 5.2 錯誤碼字典

| Code | HTTP | 描述 |
|:-----|:-----|:-----|
| `INVALID_FORMAT` | 422 | 欄位格式錯誤 |
| `REQUIRED_FIELD` | 422 | 必填欄位缺失 |
| `RESOURCE_NOT_FOUND` | 404 | 資源不存在 |
| `RESOURCE_CONFLICT` | 409 | 資源衝突 |
| `PERMISSION_DENIED` | 403 | 權限不足 |
| `RATE_LIMITED` | 429 | 超過 rate limit |
| `LLM_SERVICE_UNAVAILABLE` | 503 | LLM 服務失效 |
| `TRIZ_SOLVE_TIMEOUT` | 504 | TRIZ 求解超時（> 60s） |
| `GATE_BLOCKED` | 422 | Gate 條件未滿足 |

## 6. 安全

### 6.1 TLS

所有環境強制 HTTPS（Staging 含）。

### 6.2 Security Headers

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; ...
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
```

### 6.3 Rate Limiting

| Endpoint 類別 | Limit |
|:--------------|:------|
| 一般查詢 | 1000/min/user |
| 寫入操作 | 100/min/user |
| LLM 呼叫（TRIZ） | 30/min/user |
| 認證 | 10/min/IP |

### 6.4 OWASP Top 10 (2021)

| 弱點 | 緩解 |
|:-----|:-----|
| A01 失效存取控制 | RBAC + 所有端點檢查 ownership |
| A02 加密失效 | TLS 1.3、bcrypt + cost 12 |
| A03 注入 | SQLAlchemy parameterized query、輸入驗證（Pydantic） |
| A04 不安全設計 | Threat modeling per feature |
| A05 安全配置錯誤 | CIS Benchmark 對齊、自動掃描 |
| A06 易受攻擊元件 | Snyk + Dependabot |
| A07 認證失效 | MFA optional、session 過期 |
| A08 資料/軟體完整性 | Image signing、SBOM |
| A09 日誌不足 | 結構化日誌 + 異常告警 |
| A10 SSRF | 白名單外部 URL |

## 9. API 生命週期與版本控制

### 9.1 版本策略

- URL prefix: `/api/v1`
- Major version 變更（v2）：6 個月 deprecation buffer
- Minor / patch：向後相容

### 9.2 Deprecation 流程

```
1. 標記為 deprecated（Header: Deprecation: true）
2. 通知用戶（changelog + email）
3. 6 個月後移除
```

### 9.3 Stages

| Stage | 描述 | 公開 |
|:------|:-----|:-----|
| `internal` | 僅內部測試 | ✗ |
| `beta` | 早期客戶測試 | 限定 |
| `stable` | 公開 GA | ✓ |
| `deprecated` | 即將移除 | ✓（含警告） |
