# 內部簡報方向規劃 — RD Design Copilot

---

**文件版本**：`v1.0`
**最後更新**：`2026-04-28`
**狀態**：`Active`
**用途**：面向非專案參與者的內部簡報、主管溝通、合作洽談

---

## 1. 需求梳理

### 1.1 這次要解的真問題

這份簡報不是要回答「你做了哪些功能」，而是要回答：

1. 這個專案到底在解什麼高成本問題？
2. 為什麼值得上級看見並持續支持？
3. 為什麼值得其他團隊或外部夥伴合作？

### 1.2 對象

| 對象 | 他們真正想知道什麼 | 簡報應該怎麼說 |
|:-----|:-------------------|:---------------|
| 上級主管 / 決策者 | 值不值得投資、風險在哪、進度到哪、要不要給資源 | 用戰略價值、返工成本、知識資產、里程碑來講 |
| 潛在合作方 | 我能怎麼接入、合作後有什麼價值、需要我提供什麼 | 用合作場景、接口、資料、試點機會來講 |
| 非專案參與者 | 不想先理解整套方法論，只想先知道這件事是否重要 | 先講痛點與結果，再講方法，最後才講技術 |

### 1.3 不可偏掉的定位

1. 不能講成純 AI demo。
2. 不能講成只有 TRIZ 專家才懂的小眾工具。
3. 必須講成「把 RD 前端決策流程標準化、可追溯化、可累積化的工程流程升級平台」。

## 2. 主敘事

### 2.1 一句話母句

> RD Design Copilot 正在把 RD 前期「靠經驗、多次試錯、知識分散」的設計流程，轉成一套可追溯、可驗證、可知識累積的 AI 協作工程系統。

### 2.2 四個價值支柱

| 支柱 | 一句話 | 對上級的意義 | 對合作方的意義 |
|:-----|:-------|:-------------|:---------------|
| 問題前移 | 把設計風險從後段返工，前移到早期定義與審查 | 降低架構級返工與時程浪費 | 可更早介入，不用等出事才補救 |
| 決策可追溯 | 每個假設、矛盾、解法、gate 都能留下依據 | 減少會議靠資歷拍板 | 合作輸入可明確掛到流程節點 |
| 知識可累積 | 專案經驗不再散在人腦、會議與檔案夾 | 建立組織資產而不是一次性努力 | 外部 know-how 可沉澱成可複用模組 |
| 方法可擴張 | 從單一案例變成可複製的工程工作法 | 有機會成為團隊級能力建設 | 可從資料、驗證、流程、技術多點接入 |

### 2.3 管理語言翻譯

| 技術語言 | 簡報語言 |
|:---------|:---------|
| TRIZ / 矛盾解析 | 系統化找出 trade-off 根源並探索不妥協方案 |
| Gate / state / evidence | 可追溯的決策節點、進度狀態與證據鏈 |
| RDP-8 | 一條把問題定義、方案探索到工程落地串起來的方法 |
| WI / ICD / MC | 把概念輸出轉成工程可執行文件 |

## 3. 簡報方向

### 3.1 整體原則

1. 一頁只回答一個問題。
2. 先講商業與工程影響，再講技術細節。
3. 先讓人理解「為何重要」，再讓人理解「如何運作」。
4. 主線服務上級，副線保留合作入口。

### 3.2 建議簡報總題

可從以下三個方向選一個：

1. **把 RD 前端決策流程變成公司能力**
2. **從試錯式設計，走向可追溯的 AI 協作開發**
3. **RD Design Copilot：把概念設計從個人經驗，升級為組織流程**

## 4. 8 到 10 頁頁綱

### Slide 1 — 這件事為什麼值得看

- **標題**：RD 前期設計，現在最大的成本不是 CAD，而是太晚看見問題
- **Key message**：專案聚焦的不是「多一個 AI 工具」，而是提早處理高成本的不確定性。
- **建議視覺**：一張「前期沒處理，後期返工成本暴增」的漏斗或時間軸。

### Slide 2 — 現在的痛點是什麼

- **標題**：RD 前期常見三重困境
- **Key message**：試錯成本高、方向不明、知識分散，導致決策依賴經驗與會議。
- **建議視覺**：三欄痛點卡片，右側對應管理損失。

### Slide 3 — 我們在做的是什麼

- **標題**：這不是聊天機器人，而是一套工程決策流程系統
- **Key message**：系統把問題定義、矛盾解析、方案探索、gate 審查與知識沉澱串成閉環。
- **建議視覺**：高層流程圖，只保留 4 到 5 個大節點。

### Slide 4 — 這套方法有什麼不同

- **標題**：把「想法」轉成「可審查的工程流程」
- **Key message**：專案的核心不是生成答案，而是把每一步的假設、證據與決策節點結構化。
- **建議視覺**：`問題 → 分析 → 解法 → Gate → 文件/知識` 的鏈條圖。

### Slide 5 — 現在已經具備哪些能力

- **標題**：目前已成形的核心能力
- **Key message**：系統已能支援約束萃取、矛盾解析、方案探索、state/gate 追溯與工程文件橋接。
- **建議視覺**：五個 capability blocks。

### Slide 6 — 對公司有什麼價值

- **標題**：如果做成，會改變哪四件事
- **Key message**：更快前期判斷、更少架構級返工、更低人才依賴、更高知識複用率。
- **建議視覺**：四象限或四支柱圖。

### Slide 7 — 現在做到哪裡

- **標題**：目前進度不是完成，而是已經跨過可驗證門檻
- **Key message**：PoC 與流程框架已成形，但仍在收斂、驗證、補強場景與證據。
- **建議視覺**：`已完成 / 進行中 / 下一步` 三欄。

### Slide 8 — 為什麼現在需要合作

- **標題**：接下來缺的不是更多想法，而是更多真實場景與接口
- **Key message**：要讓系統變成組織能力，需要資料、domain feedback、驗證場景與跨部門流程接口。
- **建議視覺**：合作需求地圖。

### Slide 9 — 合作可以怎麼進來

- **標題**：四種合作入口
- **Key message**：可以從資料、流程、場域、技術四種入口低成本試點。
- **建議視覺**：四象限合作入口圖。

### Slide 10 — 希望換到什麼決策

- **標題**：這份簡報真正要換來的不是掌聲，而是下一步
- **Key message**：希望確認是否支持將 RD 前端決策流程標準化，以及先從哪個合作入口開始。
- **建議視覺**：單頁 CTA，列出 2 到 3 個可選決策。

## 5. 主管版與合作版的拆法

### 5.1 主管版強調

1. 為什麼值得持續投入。
2. 目前風險與缺口在哪。
3. 需要什麼資源或授權。
4. 成功後會形成什麼組織能力。

### 5.2 合作版強調

1. 哪些合作場景最適合先試。
2. 對方能提供什麼關鍵輸入。
3. 合作後能換到什麼成果。
4. 試點的範圍、邊界與期待輸出。

## 6. 簡報可直接用的文案骨架

### 6.1 開場 30 秒

> 我們現在做的不是再加一個 AI 工具，而是想把 RD 前期最依賴個人經驗、也最容易導致後段返工的決策流程，變成一套可追溯、可驗證、可累積的工程能力。

### 6.2 中段轉場

> 所以重點不是模型多厲害，而是能不能讓問題更早被定義、讓方案更早被審查、讓知識不再跟著人走。

### 6.3 收尾 CTA

> 如果這件事值得做，下一步不是再討論抽象方向，而是選一個合作入口，把它放進真實場景驗證。

## 7. STRIKE Prompt 模板

### 7.1 主簡報生成 Prompt

```text
S — Situation
你正在協助撰寫一份內部專案簡報，主題是 RD Design Copilot。受眾是非專案參與者，包含上級主管與潛在合作對象。這些人不熟專案細節，也不會先理解 TRIZ 或內部架構。簡報的目的不是介紹功能，而是讓他們快速理解這個專案在解什麼高成本問題、目前做到哪裡、為什麼值得支持或合作。

T — Task
請先梳理需求，再產出一份適合 8~10 頁簡報的內容策略。輸出必須包含：核心主敘事、受眾拆解、頁面結構、每頁標題、每頁一句 key message、建議視覺元素、合作入口設計，以及最後的 call to action。若輸入不足，先列資訊缺口，不要自行腦補。

R — Role
你是企業內部策略簡報顧問，擅長把技術專案翻譯成高階主管與合作夥伴都能快速理解的價值敘事。

I — Input
專案背景如下：
1. 專案名稱：RD Design Copilot。
2. 核心問題：RD 前期概念設計試錯成本高、方向不明、知識分散。
3. 核心方法：用 RDP-8 / TRIZ / Gate Review，把前期設計流程轉成可追溯、可驗證、可知識累積的 AI 協作工程系統。
4. 核心價值：降低返工、縮短前期判斷時間、降低資深人才依賴、累積組織知識。
5. 簡報用途：向上管理 + 尋找合作。
6. 目前狀態：PoC 與方法框架已成形，但仍在持續收斂與驗證。
7. 簡報定位：不能講成 AI demo，也不能講成小眾方法論介紹，必須講成工程流程升級平台。

K — KPI
輸出必須滿足：
1. 非專案參與者 3 分鐘內能懂價值。
2. 每頁只回答一個核心問題。
3. 每個技術詞都要翻譯成管理或合作語言。
4. 同時兼顧主管視角與合作方視角。
5. 明確區分「已完成 / 進行中 / 需要合作」。

E — Example
請用以下格式輸出：
- 簡報總主題
- 受眾拆解
- 主敘事
- 8~10 頁頁綱
- 每頁標題
- 每頁 key message
- 建議視覺元素
- 合作入口
- 最後一頁 CTA
```

### 7.2 Executive Summary Prompt

```text
S — Situation
我要把 RD Design Copilot 的專案價值濃縮成 1 頁 executive summary，給沒有參與專案的主管快速閱讀。

T — Task
請輸出 1 頁內的高層摘要，包含：問題、解法、目前進度、價值、風險、下一步需求。

R — Role
你是高階主管溝通顧問。

I — Input
這個專案正在把 RD 前期設計從高試錯、低追溯、知識分散，轉成可追溯、可驗證、可累積的 AI 協作工程流程。

K — KPI
1. 主管 90 秒內可讀完。
2. 不使用不必要術語。
3. 能直接支援是否投入資源的判斷。

E — Example
格式：一句話定位 / 問題 / 現在做法 / 目前進度 / 預期價值 / 需要支持。
```

### 7.3 合作邀請摘要 Prompt

```text
S — Situation
我要向可能合作的內部團隊或外部夥伴介紹 RD Design Copilot，目的是讓對方快速理解合作切入點。

T — Task
請輸出一份 1 頁合作邀請摘要，包含：合作背景、合作價值、可切入的合作入口、預期輸入、預期輸出、試點建議。

R — Role
你是 B2B 技術合作提案顧問。

I — Input
專案目前需要真實資料、驗證場景、設計規則、流程接口與 domain feedback，來把 PoC 推進成可落地的組織能力。

K — KPI
1. 對方 2 分鐘內看懂怎麼合作。
2. 清楚列出雙方交換價值。
3. 合作入口要具體，不能停在抽象願景。

E — Example
格式：合作目的 / 為何是現在 / 四種合作入口 / 試點建議 / 下一步。
```

## 8. 建議使用順序

1. 先用主簡報 Prompt 產出 8 到 10 頁骨架。
2. 再拆成主管版與合作版兩個版本。
3. 最後補案例、流程圖、數據與 appendix。

## 9. 本版涵蓋與不涵蓋

### 本版涵蓋

- 簡報需求梳理
- 主敘事與價值支柱
- 8 到 10 頁頁綱
- 主管版 / 合作版拆法
- STRIKE prompt 模板

### 本版不涵蓋

- 實際投影片設計稿
- 真實案例頁內容
- 數據圖表製作
- 簡報口語逐字稿完整版

## 10. 後續可選擴充

1. 補一頁真實案例前後對比，讓說服力從概念進入證據。
2. 補一頁「已知限制與風險」，增加管理層信任。
3. 補一版 5 頁超短版，用於高層快速過目。
