## 1. 這頁要回答的一個問題

> 不同部門現在可以怎麼參與這個系統的建構與導入？

## 2. 一句話 Key Message

> 這個系統要成為組織能力，需要的不只是模型——而是流程、資料、驗證與工程接口的共同補位。

## 4. 主要內容

### A. 四角色 × 接口 Mapping

| 角色 | 提供什麼 | 接入哪些 Phase | 預期產出 |
|:-----|:---------|:-------------|:---------|
| **PM / 產品** | 問題場景、優先順序、導入節點時機 | P0 SCOPE、G3 凍結決策 | 明確的試點問題定義 + 導入排程 |
| **RD / Domain** | 真實案例、物理約束、設計規則、失效模式 | P0-P3 全段（知識輸入） | 矛盾描述品質提升 + 解法可行性驗證 |
| **架構 / Backend** | Runtime 穩定度、tool 邊界、擴充規劃、持久化演化 | Harness 層（L2-L5） | 系統可靠度 + 新 tool 接入能力 |
| **品質 / 測試 / 製造** | 後段 gate 驗證策略、導入條件、實際量產接口 | P4-P7（TR1-TR10） | gate review 可執行性 + 量產銜接 |

### B. 四種協作接入點

| 接入點 | 說明 | 具體範例 |
|:-------|:-----|:---------|
| **資料接入** | 把散落的知識輸入系統 | 專案 lookup table、專利庫、失效模式庫、材料資料庫 |
| **流程接入** | 把現有流程節點對齊 RDP-8 | Pre-CAD review 對齊 G3、gate timing 對齊 TR schedule |
| **領域接入** | 把領域知識轉成可消費格式 | 約束規則文件化、驗證標準量化、lessons learned 結構化 |
| **技術接入** | 把外部系統連入 harness | PLM bridge、CAD plugin、測試設備 data link、ERP/MES 介面 |

### C. 目前需要的具體支持

| 需求 | 對應角色 | 為什麼現在需要 |
|:-----|:---------|:-------------|
| 一個明確試點問題 | PM + RD | 沒有真實場景，流程無法被端到端驗證 |
| 真實案例的矛盾描述 | RD / Domain | TRIZ 推理品質取決於輸入描述品質 |
| 後段 gate 退出條件確認 | 品質 / 測試 | G4-G7 的退出條件需要對齊實際標準 |
| Harness runtime 穩定化 | 架構 / Backend | 多 agent 調度、state 驗證、錯誤恢復需補強 |
| 跨部門接口窗口指定 | 管理層 | 需要明確對口才能推進協作 |

### D. CTA（Call to Action）

```
Step 1 ──→ Step 2 ──→ Step 3

選一個          選一個           定義下一輪要
試點場景        合作接口          驗證的 gate
                               / capability
```

**Step 1：選試點場景**
- 挑一個正在進行、有明確痛點的設計問題
- 理想特徵：有矛盾、有資料、有急迫性

**Step 2：選合作接口**
- 從四種接入點（資料/流程/領域/技術）中選最容易啟動的一個
- 建議從「領域接入」開始——投入最低、價值最直接

**Step 3：定驗證 gate**
- 確認本輪試點要走到哪個 Gate
- 建議第一輪目標：走完 P0→P3（問題定義到概念凍結），驗證前端流程可行性

## 6. 口條骨架（25 秒）

> 最後這一頁是協作地圖。上面四個欄位分別是 PM、RD、架構跟品質——每個角色可以提供什麼、接入哪一段。下面是三個行動步驟：第一，選一個真實試點；第二，選一個最容易啟動的接口；第三，定好本輪要驗證到哪個 gate。我們建議第一輪先走 P0 到 P3，驗證前端流程的可行性。
