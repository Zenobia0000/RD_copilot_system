# 現狀用戶旅程圖 (Current-State User Journey Map)

> **版本**: v1.0 | **日期**: 2026-04-13
> **說明**: 描述 RD 工程師在「沒有 RD Design Copilot」時的概念設計現狀旅程，用於識別痛點與機會點。
> **驗證狀態**: 團隊假設 — 待客戶訪談驗證 (see E1x--user-research-synthesis.md)

---

## 旅程總覽

本圖涵蓋三個核心角色在硬體早期概念設計階段的現狀工作流程。
重點不在未來產品功能，而在**當前流程中隱藏的摩擦與浪費**。

### 已識別的六大痛點主題 (PRD §3.3)


| 代碼       | 痛點                                | 說明                               |
| -------- | --------------------------------- | -------------------------------- |
| **PP-1** | 經驗鎖定 (Path Dependency)            | 資深工程師傾向重複使用過去方案，新人則無經驗可依循        |
| **PP-2** | 假設隱藏 (Hidden Assumptions)         | 關鍵設計假設停留在個人腦中，未被顯式記錄或挑戰          |
| **PP-3** | 風險後置 (Late Risk Discovery)        | 結構性風險直到 Proto 或量產階段才被發現，修改成本 10x |
| **PP-4** | 決策不可追溯 (Untraceable Decisions)    | 設計審查後無法回溯「當時為何選 A 而非 B」          |
| **PP-5** | 溝通斷層 (Communication Gaps)         | RD、PM、主管各自使用不同語言描述同一問題           |
| **PP-6** | 證據缺口不可見 (Invisible Evidence Gaps) | 無人知道哪些 KPI 仍缺乏量化驗證依據             |

## Persona 1: 資深 RD 工程師 張三 (Primary)

> **背景**: 機構設計 8 年經驗，負責 e-Bike 驅動系統模組。習慣 SolidWorks + Excel 作業。
> **目標**: 在 2 週內產出可行概念方案，通過設計審查。

### 旅程階段

#### 階段 1: 收到任務


| 維度     | 內容                                        |
| ------ | ----------------------------------------- |
| **行動** | 收到 PM 轉發的客戶規格書（PDF/Email），快速瀏覽重點          |
| **工具** | Email、Teams、PDF Reader                    |
| **想法** | 「這份規格書寫得很模糊，到底要什麼等級的防水？」                  |
| **情緒** | 😐 中性偏疑惑                                  |
| **痛點** | **PP-5 溝通斷層** — 規格書用商業語言撰寫，缺乏工程定義；需反覆來回確認 |
| **機會** | 自動將商業規格翻譯為工程約束條件與可量測 KPI                  |


#### 階段 2: 理解問題


| 維度     | 內容                                                               |
| ------ | ---------------------------------------------------------------- |
| **行動** | 翻閱過去類似專案的資料夾、詢問同事、搜尋供應商 Datasheet                                |
| **工具** | 公司 NAS、Google、供應商網站、個人筆記                                         |
| **想法** | 「上次那個案子好像用過類似結構，直接拿來改應該最快」                                       |
| **情緒** | 😊 熟悉感帶來的安心                                                      |
| **痛點** | **PP-1 經驗鎖定** — 直覺搜尋過去方案，未系統性探索問題空間；**PP-2 假設隱藏** — 心中已有預設答案但未明說 |
| **機會** | 結構化的問題拆解流程，強制列出隱含假設再開始發想                                         |


#### 階段 3: 發想方案


| 維度     | 內容                                               |
| ------ | ------------------------------------------------ |
| **行動** | 在紙上或 SolidWorks 草繪 1-2 個方案，多為過去設計的變形             |
| **工具** | SolidWorks、紙筆、Excel                              |
| **想法** | 「時間不夠，先做一個穩的方案，審查時再說」                            |
| **情緒** | 😤 時間壓力下的焦躁                                      |
| **痛點** | **PP-1 經驗鎖定** — 方案數量不足（通常 1-2 個），且同質性高；缺少系統性創新方法 |
| **機會** | TRIZ / SCAMPER 等結構化創新方法，強制產出 3+ 異質方案             |


#### 階段 4: 評估篩選


| 維度     | 內容                                                         |
| ------ | ---------------------------------------------------------- |
| **行動** | 憑經驗在心中快速比較，有時做簡單 Excel 打分表                                 |
| **工具** | Excel、心算                                                   |
| **想法** | 「方案 A 比較保險，B 有風險但性能好……算了選 A」                               |
| **情緒** | 😰 對選擇的不確定感                                                |
| **痛點** | **PP-3 風險後置** — 未做系統性風險分析，憑直覺判斷；**PP-4 決策不可追溯** — 篩選邏輯未被記錄 |
| **機會** | MUST/WANT 結構化評估 + 風險矩陣，決策過程自動留痕                            |


#### 階段 5: 設計審查


| 維度     | 內容                                                                           |
| ------ | ---------------------------------------------------------------------------- |
| **行動** | 準備 PPT 簡報，在會議中向主管報告方案                                                        |
| **工具** | PowerPoint、投影機                                                               |
| **想法** | 「希望主管不要問太刁鑽的問題，有些數據我還沒驗證」                                                    |
| **情緒** | 😰 緊張不安                                                                      |
| **痛點** | **PP-6 證據缺口不可見** — 不確定哪些論點有數據支撐、哪些只是推測；**PP-2 假設隱藏** — 審查者難以辨識哪些是已驗證事實、哪些是假設 |
| **機會** | 自動標記證據缺口，審查前即可看到哪些論點需要補充數據                                                   |


#### 階段 6: 決策定案


| 維度     | 內容                                          |
| ------ | ------------------------------------------- |
| **行動** | 主管口頭拍板，張三開始做細部設計                            |
| **工具** | 會議記錄（如果有人寫的話）                               |
| **想法** | 「OK 定了，但如果後面出問題，當初為什麼選這個方案？」                |
| **情緒** | 😐 鬆一口氣但隱隱不安                                |
| **痛點** | **PP-4 決策不可追溯** — 決策理由散落在會議記錄或根本沒記錄；半年後無法回溯 |
| **機會** | 結構化決策記錄，自動關聯方案評估數據與決策理由                     |

## Persona 2: RD 主管 李四

> **背景**: 研發部門主管，管理 6 位 RD 工程師。需同時掌握多個專案進度與技術風險。
> **目標**: 確保團隊產出的設計方案品質足夠、風險可控，在時程內完成。

### 旅程階段

#### 階段 1: 分派任務


| 維度     | 內容                                             |
| ------ | ---------------------------------------------- |
| **行動** | 收到 PM 的專案需求後，評估工作量並分配給合適的工程師                   |
| **工具** | Email、Teams、Excel 排程表                          |
| **想法** | 「這個案子比較複雜，派給張三比較穩，但他手上已經有兩個案子了」                |
| **情緒** | 😐 日常但隱含資源焦慮                                   |
| **痛點** | **PP-5 溝通斷層** — 任務需求從 PM 到主管到 RD 經過多層轉譯，資訊逐漸失真 |
| **機會** | 統一的任務定義格式，從源頭減少轉譯損失                            |


#### 階段 2: 中期檢視


| 維度     | 內容                                          |
| ------ | ------------------------------------------- |
| **行動** | 走到工程師座位旁口頭詢問進度，或在週會中聽取報告                    |
| **工具** | 口頭、週會 PPT                                   |
| **想法** | 「張三說進度正常，但我不確定他探索了多少方案空間」                   |
| **情緒** | 😰 資訊不透明的焦慮                                 |
| **痛點** | **PP-6 證據缺口不可見** — 無法即時看到每個專案的假設驗證狀態與方案探索廣度 |
| **機會** | 即時儀表板顯示各專案的探索廣度、假設驗證率、風險狀態                  |


#### 階段 3: 設計審查


| 維度     | 內容                                                                            |
| ------ | ----------------------------------------------------------------------------- |
| **行動** | 主持審查會議，聽取方案報告，提出質疑，做出判斷                                                       |
| **工具** | 會議室、PPT、白板                                                                    |
| **想法** | 「這個方案聽起來合理，但我怎麼知道他有沒有漏掉什麼重要風險？」                                               |
| **情緒** | 😤 時間有限卻要做高品質判斷的壓力                                                            |
| **痛點** | **PP-2 假設隱藏** — 審查時難以辨別哪些結論基於驗證數據、哪些基於未驗證假設；**PP-3 風險後置** — 審查時常發現「應該早點考慮」的風險 |
| **機會** | 審查前自動產生假設/風險/證據缺口報告，提升審查效率與深度                                                 |


#### 階段 4: 最終決策


| 維度     | 內容                                       |
| ------ | ---------------------------------------- |
| **行動** | 綜合各方意見做出最終拍板，有時需要向上級報告                   |
| **工具** | 會議記錄、Email                               |
| **想法** | 「我選了方案 A，但萬一出問題，我能拿出什麼依據說明當時的判斷？」        |
| **情緒** | 😰 決策責任的壓力                               |
| **痛點** | **PP-4 決策不可追溯** — 決策依據散落各處，事後難以重建當時的判斷脈絡 |
| **機會** | 自動生成決策追溯報告，完整記錄從問題定義到最終選擇的全路徑            |

## Persona 3: 專案經理 王五

> **背景**: 負責跨部門專案協調，需在客戶需求、RD 能力、時程之間取得平衡。
> **目標**: 確保專案按時交付、客戶需求被正確轉譯、各部門資訊對齊。

### 旅程階段

#### 階段 1: 需求轉譯


| 維度     | 內容                                          |
| ------ | ------------------------------------------- |
| **行動** | 將客戶需求整理為內部規格書，發給 RD 團隊                      |
| **工具** | Word、Email、客戶提供的 PDF/Excel                  |
| **想法** | 「客戶說要『輕量化』，到底是輕多少？我先寫個大概，讓 RD 自己判斷」         |
| **情緒** | 😤 客戶需求模糊帶來的挫折                              |
| **痛點** | **PP-5 溝通斷層** — 客戶語言到工程語言的轉譯缺乏結構化方法，容易遺漏或誤解 |
| **機會** | AI 輔助將模糊需求轉為可量測的工程約束條件                      |


#### 階段 2: 進度追蹤


| 維度     | 內容                                        |
| ------ | ----------------------------------------- |
| **行動** | 逐一詢問各部門進度，手動更新 Excel 甘特圖                  |
| **工具** | Excel、Teams、週會                            |
| **想法** | 「RD 說還在評估方案，但我不知道他們到底做到哪一步了」              |
| **情緒** | 😰 進度不透明的焦慮                               |
| **痛點** | **PP-6 證據缺口不可見** — 無法量化概念設計階段的完成度，只能靠口頭回報 |
| **機會** | 可視化的設計階段進度指標（假設驗證率、方案數、風險覆蓋率等）            |


#### 階段 3: 跨部門對齊


| 維度     | 內容                                                                  |
| ------ | ------------------------------------------------------------------- |
| **行動** | 組織跨部門會議，協調 RD、採購、品質、製造的需求衝突                                         |
| **工具** | 會議室、PPT、白板                                                          |
| **想法** | 「RD 說技術上做得到，採購說成本太高，到底誰的資訊是對的？」                                     |
| **情緒** | 😤 各方說法矛盾的挫折                                                        |
| **痛點** | **PP-5 溝通斷層** — 各部門使用不同指標與語言，缺乏共同的事實基礎；**PP-2 假設隱藏** — 各方論述中的假設未被揭露 |
| **機會** | 統一的數據平台，讓跨部門討論基於相同的事實與假設                                            |


#### 階段 4: 報告產出


| 維度     | 內容                                                                       |
| ------ | ------------------------------------------------------------------------ |
| **行動** | 彙整各部門資料，製作進度報告給客戶或高層                                                     |
| **工具** | PowerPoint、Excel、Word                                                    |
| **想法** | 「又要做報告了，得從各個管道把資料撈出來拼在一起……」                                              |
| **情緒** | 😤 重複性勞動的不耐                                                              |
| **痛點** | **PP-4 決策不可追溯** — 報告中的數據來源分散，難以追溯；**PP-6 證據缺口不可見** — 不確定報告中哪些數字是實測、哪些是估算 |
| **機會** | 一鍵匯出完整設計報告，自動標註數據來源與信心度                                                  |

## 情緒曲線總覽

```
情緒
 😊 ┤          
    │  ·(張三:理解問題)
 😐 ┤·                                                    ·(張三:決策定案)
    │  ·(李四:分派)     ·(王五:追蹤)
 😰 ┤                 ·        ·(張三:評估)  ·(李四:決策)
    │                           ·(張三:審查)  ·(王五:對齊)
 😤 ┤        ·(張三:發想)                      ·(王五:報告)
    │  ·(王五:轉譯)                ·(李四:審查)
    └──────────────────────────────────────────────────────→ 時間
      收到任務    理解問題    發想方案    評估篩選    審查決策
```

**關鍵洞察**: 旅程情緒在「發想」到「審查」區間達到最低點。這正是概念設計最關鍵的區間，也是 RD Design Copilot 應優先介入的階段。

## 痛點-機會矩陣


| 痛點           | 影響頻率    | 影響程度          | 相關角色     | 優先改善順序 |
| ------------ | ------- | ------------- | -------- | ------ |
| PP-1 經驗鎖定    | 每次專案    | 高 — 方案品質天花板   | 張三       | 1      |
| PP-2 假設隱藏    | 每次專案    | 高 — 審查無法深入    | 張三、李四、王五 | 2      |
| PP-3 風險後置    | ~60% 專案 | 極高 — Proto 重工 | 張三、李四    | 3      |
| PP-4 決策不可追溯  | 每次專案    | 中 — 知識無法積累    | 張三、李四、王五 | 4      |
| PP-5 溝通斷層    | 每次專案    | 中 — 需求失真      | 王五、李四    | 5      |
| PP-6 證據缺口不可見 | 每次專案    | 中 — 品質盲區      | 李四、王五    | 6      |
